# Company workspace foundation — localhost

This records build-order item 5's local membership foundation and subsequent exact-offer approval increment. It adds company workspaces, local invitations, employee/approver memberships, member revocation and selection of the workspace receiving new tasks. Stripe remains disconnected; hosted staging and the public demo are unchanged.

## Boundaries and acceptance criteria

- Local identity owns users, memberships and invitations in the existing SQLite identity database. Application tasks remain in native PostgreSQL. The paired backup must restore both. This extends the existing local identity boundary; it does not activate or migrate managed authentication.
- Invitations have 256-bit random tokens, only hashes persisted, a 24-hour expiry and an exact recipient-email binding. Only the link creator receives the raw token once. Lost responses require revoking the outstanding invitation and creating another; a repeated request never silently creates two active invitations.
- Recipients sign in and explicitly review the company and role before accepting. Duplicate acceptance is harmless while membership still exists; accepted-link replay cannot restore removed membership. No email is sent from localhost.
- Administrators are workspace owners. Only they can view the member directory and invite/revoke/remove access. Employee and approver roles cannot grant access or remove the owner. Every team mutation records an audit event.
- Each HTTP request reloads current memberships. Revocation blocks subsequent task access; already authorized in-flight requests are not retroactively cancelled. Task data remains available to the company administrator after removal.
- Company task creation and listing use the selected workspace. Employees see their own tasks; owners can see all tasks. Personal workspaces stay separate. The composer identifies the current destination. Selection is in-memory and defaults to personal after a full reload.
- Approver memberships now authorize exact-offer budget decisions; see the second increment below. Real-money corporate funding remains disabled.

## Implemented local routes

`POST /api/teams` creates a company with idempotency. `GET /api/teams/:id` returns role-appropriate detail. `POST /api/teams/:id/invite` generates an invitation, `POST /api/teams/preview` validates the signed-in recipient and returns company/role, and `POST /api/teams/accept` joins atomically. `POST /api/teams/:id/remove` removes a non-owner membership or revokes a pending invitation. All mutations use the existing authenticated CSRF boundary. Invitation secrets are passed in POST bodies; links use URL fragments, which the app removes after reading.

## Exact-offer approvals and allowance reservations (28 October 2026)

The second local increment adds a fixed USD company allowance, requests from employees/owners, decisions by approvers/owners, and decline/resubmit on the original task. All company tasks, including owner requests, require explicit approval. Owners may approve their own requests in this local policy; separation of duties and approval thresholds remain release decisions. Approvers see the submitted scope, offer and request reason, not the employee's entire private conversation or files.

Approval binds the complete immutable offer, selected offer ID, scope version, title, brief and input hash. Conversation messages do not alter it. Offer selection, scope/input change or closing the request invalidates approval and releases its allocation in the same application transaction. A new submission has a new approval ID; old decisions cannot approve it. Prior decisions remain labelled as previous requests. Decisions have version checks and durable idempotency receipts.

An administrator sets a total allowance, not a recurring monthly budget. Approval atomically reserves the quoted USD amount. Every task mutation uses task → assigned agent → company budget lock order. Parallel approvals on independent database connections cannot overbook the allowance. It cannot be lowered below active reservations and commitments. Expired unstarted reservations are excluded by time in the authoritative budget calculation, without needing a background sweep. Starting an unpaid task or initiating sandbox checkout commits its allocation; unpaid acceptance/cancellation/failure releases it, while money-related commitments remain through reconciliation until an expired checkout or confirmed full refund. Refund failures retain the commitment. These are authorization records, not an accounting ledger or real escrow.

Funding/start revalidates the exact agreement, allocation and current approver membership. A removed approver cannot authorize new work through a saved decision. Identity remains a separate SQLite authority: an already authorized in-flight operation is not retroactively revoked. Real-money deployment requires a unified membership/financial transaction boundary or an equivalent reviewed revocation design. Membership is refreshed on subsequent requests.

Routes: `GET/POST /api/teams/:id/budget`, `POST /api/tasks/:id/approval`, `POST /api/tasks/:id/approval/decide`. Task detail exposes approval and the task list exposes its status. Queue results use explicit cursor pagination. Employees see only their own requests. Refund controls remain owner-only; approved employees can initiate fixture funding and retrieve the existing checkout link. Stripe is disconnected in the local launcher.

Validation: SQLite/PGlite regressions cover decline/resubmit, message preservation, changed-offer invalidation, stale decisions, expiry, roles, revoked approver, duplicate decisions, competing allocations, protected limits, fixture funding and refund/reapproval. Native PostgreSQL tests exercise competing reservations across separate pools, employee start gating, commit/release, and the existing restart/paired-backup suite. Browser QA used disposable native PostgreSQL data to request approval, decline, resubmit on the same task, approve and observe the $35 reservation against a $100 allowance. UI uses existing conversation cards and business panels. No provider or real-money validation is implied.

Remaining limits: allowance history is bounded to 1,000 allocations (explicit refusal at the cap); no monthly rollover, multi-currency, tax/fee treatment, partial refunds, automated notifications or approval delegation. Persistent company workspace selection, hosted identity parity and independent human security/payment review remain open. Expired history may be displayed without a materialized expiry audit event; the budget calculation and start gate enforce expiry directly.

## Local administration increment — 28 October 2026

Administrators can change an employee to an approver or back, remove members with an inline confirmation, and read paginated access history. Role changes compare the submitted previous role inside the identity transaction; stale edits fail rather than overwriting a different current role. Owners cannot be demoted or removed through these controls. Role updates and their before/after audit entries commit together. History is owner-only, escaped in the UI, and paged using a tenant-scoped cursor. Existing invite/removal events are retained by additive migration 005.

Validation: 11 team/approval tests passed; frontend regression suite passed. Disposable native-PostgreSQL browser QA exercised approver demotion, inline employee removal and the resulting history entries, using existing prototype panels and controls. User records, demo and staging were not used as fixtures. A paired local backup preceded the main local restart.

Limits: this is local identity administration, not hosted identity parity or unified cross-database authorization. Revocation is rechecked on subsequent requests; actions already in progress are not atomically revoked. Existing approvals still depend on the current reviewer role; demotion/re-promotion epochs and automatic reservation invalidation need a separate permission-version design before production. Expected-role comparison does not detect a role changed away and back between reads. Ownership transfer and mobile browser QA remain open. No Stripe connection or real-money validation was performed.

## Revocation cutoff and approval epochs — 29 October 2026

This supersedes the local in-flight and demotion/re-promotion limitations above. Local application actions and membership mutations now share an access boundary. Native PostgreSQL uses a database advisory transaction lock, with a process queue before borrowing a connection; SQLite tests use a serial queue. An action which acquired the boundary first may finish before removal succeeds. After successful removal, queued actions refresh membership before reads, writes and receipt replay. Background task writes reacquire the boundary and reload the current actor. This is an ordered cutoff, not rollback of already completed actions or erasure of files already downloaded.

Identity migration 006 retains monotonically increasing membership epochs across role changes, removal and re-invitation. Approval requests and decisions snapshot their respective membership epochs. Access changes stale pending/approved records and release unused reservations. Promoting the same reviewer again cannot revive their old decisions. Old successful decision retries fail as stale. Active execution and funded commitments remain recorded; access removal does not silently cancel work or manufacture refunds.

Identity changes commit before application invalidation. If the process fails between these writes, the next guarded action reconciles epochs before proceeding. Legacy approvals without epochs require fresh approval. Reconciliation is paginated and retains task audit events. The UI explains why a new request is needed, on the same task.

Evidence: five focused local access tests cover paused-action races, queued mutations, stale reads and receipt replays, demotion/re-promotion, remove/re-invite, adapter restart and interrupted invalidation with active commitments. The native PostgreSQL suite passes 21 tests including cross-pool lock ordering, lock release on failure, HTTP delivery, database restart and paired backup recovery. Final full regression suite passed 154 tests; frontend/shared UI passed 30 tests. Browser QA on disposable native data verified $35 reserved → role demotion → $0 reserved/$100 available, re-promotion retaining stale status, and resubmission on the same task.

Boundaries: the access lock is deliberately coarse for localhost and has not been load-qualified for production scale. All processes must use this adapter against the same identity authority and application database; direct database administration is not a supported concurrent access path. Hosted/managed identity parity and independent security review remain release work. External actions already dispatched and bytes already authorized cannot be recalled. Stripe remains disconnected; no deployment occurred.
